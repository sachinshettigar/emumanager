# Understanding the Emulator Studio codebase

A guided tour for a human (or agent) who has never seen this repo. `docs/architecture.md` is the
**reference** — the fixed shape and the rules. This document is the **orientation** — how to read
the code, the mental models that make it click, and how to add a feature without breaking the
grain of the thing.

Read `AGENTS.md` first (it's the operating manual). Then this. Then start tracing code.

---

## 1. What this app is, in one paragraph

A desktop app (Tauri v2: a Rust process + a web UI) that lets you create, launch, track and share
Android emulators **without installing Android Studio**. It does that by managing Google's
command-line SDK for you — `sdkmanager`, `avdmanager`, `emulator`, `adb` — downloading them into
its own data directory, and driving them as a human would. Everything the app "knows" beyond what
those tools report (which profile an emulator came from, your tags and notes, its last run state)
lives in a small SQLite database. Scope is **Android only** and that is deliberate
([ADR 0003](adr/0003-android-only-scope.md)).

---

## 2. The five layers, and the one rule

```
src/                     the web UI (React + TypeScript)
  │  window.__TAURI__ invoke() + event listeners, every call typed
src/lib/bindings.ts      GENERATED — the typed seam. Never hand-edit.
  │
src-tauri/               the "shell": #[tauri::command] functions, event structs, DI wiring
  │  constructs the real adapters and hands them to…
crates/emu-core/         ALL the domain logic. Knows nothing about Tauri or the OS.
  │  every side effect is a trait ("port"); tests inject fakes
crates/emu-android/      the one real Provider impl — wraps sdkmanager/avdmanager/emulator/adb
crates/emu-host/         host inspection (virtualization, accelerator, disk, RAM)
crates/emu-helper/       a separate tiny elevated binary (enable WHPX, add kvm group, …)
```

**The rule that holds the whole thing together:** `crates/emu-core` depends on `tauri` in
*neither* `[dependencies]` nor `[dev-dependencies]`. `scripts/emu-core-no-tauri.sh` enforces it in
`just validate`. Consequence: all the interesting logic is testable with plain `cargo test`, no
app, no windowing, no Android binaries. When you're deciding where code goes, ask "could this be
unit-tested without a running app?" — if yes, it belongs in `emu-core`.

`src-tauri` is glue. If you find yourself writing an `if`/`match` with real decision-making in a
`#[tauri::command]`, it probably wants to move down into `emu-core`.

## 3. The one idea to internalise: ports and adapters

Every time the domain needs to touch the outside world — run a process, download a file, read the
clock, read the filesystem — it goes through a **trait** defined in `crates/emu-core/src/ports.rs`
(or `provider.rs`). Real code passes a real implementation; tests pass a fake.

```rust
// emu-core defines the port:
#[async_trait]
pub trait ProcessRunner: Send + Sync {
    async fn run(&self, cmd: Command) -> Result<Output>;          // run to completion
    async fn spawn(&self, cmd: Command) -> Result<Box<dyn ChildProcess>>; // long-lived / streaming
}

// src-tauri/src/ports/process.rs implements it for real (tokio::process).
// emu-core/src/testing/mod.rs implements FakeProcessRunner: you script
//   .on_run("sdkmanager --licenses", ok("All SDK package licenses accepted"))
//   .on_spawn("emulator @pixel6_api34", ["line 1", "line 2"], ok(""))
// and it records every call for assertions.
```

The ports are: `ProcessRunner`, `Downloader`, `HostProbe`, `Clock`, `Fs`, and the big one,
`Provider` (`crates/emu-core/src/provider.rs`) — the whole emulator lifecycle surface
(`list_devices`, `ensure_image`, `create`, `launch`, `stop`, `delete`, `reconcile`).

`emu-android::AndroidProvider` is the only `Provider` implementation. It also carries a pile of
*inherent* methods (`detail`, `rename`, `set_hardware`, `logcat_start`, `device_facts`, …) that
aren't on the trait because only the Tauri commands call them and keeping the trait small keeps a
future remote/cloud provider plausible.

**Why this matters when reading:** when you see `self.process.run(...)` in `emu-android`, you're
looking at the seam. The behaviour on the other side of it is either a real subprocess or a
scripted fake, and the test right next to the code tells you which strings it expects.

## 4. The typed IPC seam

`src/lib/bindings.ts` is generated by `tauri-specta` from the Rust `#[tauri::command]` signatures
and every `#[derive(specta::Type)]` struct. **It is the only Rust↔TS interface.** Rules:

- Change a command signature or a DTO → run `just bindings` → commit the regenerated file.
  `lefthook`'s pre-commit hook does this for you if you commit through git normally, which is why
  the `git diff --exit-code src/lib/bindings.ts` step in `just validate` "fails" locally until you
  commit — that's expected, not a bug.
- `specta-typescript` won't export `u64`/`i64` (bigint risk). Narrow to `u32` in the DTO with
  `u32::try_from(x).unwrap_or(u32::MAX)`. Every real size in this app fits.
- A command returning a bare value (no `Result`) — like `app_info()` — generates a binding that
  returns the value directly, *not* the `{status, data}` envelope.

On the TS side, `src/lib/ipc.ts` wraps every generated call:

```ts
function unwrap<T>(res: Envelope<T>): T {
  if (res.status === "error") throw new IpcCallError(res.error); // a real Error, .ipc has {code,message}
  return res.data;
}
```

and exposes **TanStack Query hooks** (`useEmulators`, `useComponents`, `useDeviceFacts`, …) and
**mutation hooks** (`useLaunchEmulator`, `useInstallComponent`, …). Components never call
`commands.*` directly; they call a hook. Tests `vi.mock("../lib/bindings", …)` and assert on the
mocked `commands.*`.

### Events (streaming)

Progress and logs don't fit request/response, so they're **typed events**:

```rust
#[derive(Serialize, specta::Type, tauri_specta::Event)]
#[tauri_specta(event_name = "job://emulator")]
pub struct EmulatorJob { pub job_id: String, pub payload: EmulatorJobKind }
// EmulatorJobKind is a tagged enum: Progress{phase,pct} | Log{line} | Done{ok,error}
```

Emitted with `.emit(&app)`. The frontend subscribes in a `useEffect` (`events.jobEmulator.listen`)
and folds each event into local state with a reducer (`applyEmulatorJobEvent` in `ipc.ts`). There
are three event channels today: `job://bootstrap` (SDK install), `job://emulator` (create/launch),
`device://log` (logcat). Same pattern each time.

The bridge between `emu-core` (which must not depend on an async runtime's channels) and the
event system is `JobHandle` (`crates/emu-core/src/model/job.rs`): a plain callback wrapper.
`emu-core` calls `job.report(Progress::log("…"))`; `src-tauri` builds the `JobHandle` with a sink
that turns each `Progress` into an emitted event. Tests build one with `JobHandle::collector()`
and assert on the captured `Vec<Progress>`.

## 5. The registry (what the app remembers)

`crates/emu-core/src/registry/` — a typed API over `sqlx` + SQLite (`migrations/`). One row per
tracked emulator (`EmulatorRow`), plus saved profiles and host snapshots. Compound values
(`Hardware`, `EmulatorSource`, tags) are **JSON text columns**, so adding a field to `Hardware`
needs no migration — just a serde change.

The registry stores *our* metadata. Ground truth (does this AVD exist? is it running?) comes from
`avdmanager` / `adb`. `AndroidProvider::reconcile()` re-reads ground truth and updates the rows so
the DB never drifts: it adopts AVDs it finds but doesn't track, flags rows whose AVD vanished as
`Error` (never hard-deletes — that's an explicit `delete`), and resets a `Running` row that's gone
from `adb devices` back to `Stopped`. `reconcile()` runs once at startup and on the Dashboard's
"Refresh".

## 6. Trace a feature end to end — "click Launch"

This is the exercise that makes the codebase legible. Follow it in the editor.

1. **UI**: `src/routes/Dashboard.tsx`, `EmulatorRow` → the Launch `<button>`'s `onClick` calls
   `launch.mutate(emulator.id)` where `launch = useLaunchEmulator()`.
2. **Hook**: `src/lib/ipc.ts` `useLaunchEmulator` → `mutationFn` calls
   `unwrap(await commands.launchEmulator(id))`.
3. **Binding**: `src/lib/bindings.ts` (generated) → `__TAURI_INVOKE("launch_emulator", { id })`.
4. **Command**: `src-tauri/src/commands/emulator.rs` `launch_emulator` → gets the shared provider
   (`mgr.get().await?`), builds a `JobHandle` bound to `job://emulator` with jobId `launch:<id>`,
   builds `LaunchOpts` via `launch_opts_for` (which reads the device profile's skin when the
   emulator's `device_frame` is on — see task 0035), calls `provider.launch(id, opts, &job)`, and
   on the result emits a terminal `EmulatorJobKind::Done`.
5. **Provider**: `crates/emu-android/src/provider.rs` `launch` → resolves the AVD name from the
   registry, builds `emulator @<avd>` + flags (`-no-window`, `-gpu`, `-skin`/`-skindir`, …),
   `self.process.spawn(cmd)`, tees output to `<data_dir>/logs/<avd>.log` **and** onto the job,
   polls `adb -s <serial> shell getprop sys.boot_completed` until `1` or a timeout, stores the
   child handle in `self.running` so `stop` can reap it, returns a `RunningHandle`.
6. **Back up**: `Done{ok:true}` event → `applyEmulatorJobEvent` flips `running` false → the
   Dashboard row re-renders as "Running" (it also polls `list_emulators` every few seconds).

Every arrow in that chain has a test: `Dashboard.test.tsx` (the click), `ipc.test.tsx` (the
unwrap), `emulator.rs` command tests are thin, `provider.rs` `launch_*` tests (the argv and the
poll loop, with `FakeProcessRunner`).

## 7. How to add a feature (the recipe)

Say you want "show the emulator's battery level". Working backwards from the UI:

1. **Domain first.** Does `emu-core` / `emu-android` already expose the data? If not, add an
   inherent method to `AndroidProvider` (or a port method if it's a genuinely new kind of side
   effect). Drive it through `self.process` / `self.fs` so it's fake-testable. Write the unit
   test *with the fixture* — if you're parsing tool output you don't have a capture of, get one
   (`--help`, a real run) and commit it; **never invent the format** (`AGENTS.md` §6.2).
2. **DTO + command.** Add a `#[derive(Serialize, specta::Type)]` DTO in `src-tauri/src/commands/`
   and a thin `#[tauri::command]` that calls the domain method and maps `CoreError` → `IpcError`.
   Register it in `src-tauri/src/lib.rs` `collect_commands![...]`. If it's a stream, add a
   `tauri_specta::Event` struct and register it in `collect_events![...]`.
3. **Regenerate.** `just bindings`. Commit the `bindings.ts` diff.
4. **Hook.** Add a `useQuery`/`useMutation` hook in `src/lib/ipc.ts` that wraps the new
   `commands.*` via `unwrap`.
5. **UI.** Consume the hook in a component. One component per file. Data comes from the hook,
   never a raw `invoke`.
6. **Tests.** A Rust unit test for the domain method; a Vitest for the component/hook (mock
   `../lib/bindings`). `knip` will flag an exported hook nothing imports — so export only what's
   used, and import a type by name if `knip` says it's an unused export but it *is* in a public
   signature.
7. **Gate + paper trail.** `just validate` green. Tick the task's acceptance criteria, update
   `PROGRESS.md`, `.agent/state.json`, and append a journal entry (`docs/playbooks/update-progress.md`).
   Conventional Commit referencing the task id.

The 8-item batch (tasks `0032`–`0038`) is seven worked examples of exactly this loop — read those
task files and their journal entries to see the recipe applied, including where corners were cut
honestly and noted.

| You want to… | Look in |
| --- | --- |
| add/inspect a Tauri command | `src-tauri/src/commands/{emulator,toolchain,profile,host,device}.rs`, register in `src-tauri/src/lib.rs` |

| parse SDK tool output | `crates/emu-android/src/{devices,sysimg,catalog,avd_list}.rs` + `crates/emu-android/tests/fixtures/` |
| touch the SDK install/uninstall flow | `crates/emu-core/src/toolchain/{bootstrap,uninstall,installed_state}.rs` |
| change the `.emuprofile` format | `crates/emu-core/src/model/profile.rs` **and** `schemas/emuprofile/v1.schema.json` (kept in sync by a test) |
| touch host-readiness detection | `crates/emu-host/src/` (`build_report` is the pure verdict fn) |
| add a frontend screen | `src/routes/*.tsx` + `src/router.tsx` + `src/nav.ts` + `src/components/icons.tsx` |
| wrap a command for the UI | `src/lib/ipc.ts` |
| the design tokens | `src/styles/tokens.css` (IBM Plex; blue primary; green = running/installed; amber = attention) |
| the dev commands | `justfile` (source of truth; mirrored in `package.json` scripts) |
| current state / what's next | `.agent/state.json`, `.agent/tasks/NNNN-*.md`, latest `.agent/journal/*.md`, `PROGRESS.md` |

## 9. The dev loop and its gotchas

- `just check-fast` — inner loop (fmt, `tsc`, `clippy -D warnings`, changed-crate tests).
- `just validate` — the gate. Runs everything CI runs. Must be green (zero warnings) on `main`.
- `just bindings` — regenerate `src/lib/bindings.ts` after any command/DTO change.
- `just dev` — run the app.

Gotchas that will bite you once:

- **`bindings.ts` diff during `just validate`** is normal after a command change — `lefthook`
  stages the regen at commit time, then the pre-push `just validate` is clean.
- **`knip`** (unused exports) and **`markdownlint`** run in `just validate` but *not* in the
  pre-commit hook — so a commit can pass locally and the pre-push validate then fails. Run
  `just validate` yourself before pushing a docs- or exports-heavy change. `markdownlint` wants
  `*asterisk*` emphasis, not `_underscore_`.
- **`pnpm tauri build` overwrites `dist/index.html`** (a committed M0 placeholder) — `git checkout
  -- dist/index.html` before committing after a build.
- **`progress-check.mjs`** fails the whole gate if a `.agent/tasks/NNNN-*.md` file has no matching
  row in `.agent/state.json` `tasks[]`, or if a task's `status` disagrees between the two. Add the
  row and keep the statuses in sync.
- **jsdom** lacks `File.arrayBuffer` (use `FileReader`) and `navigator.clipboard` (guard with
  `?.`). `<details>` keeps collapsed children in the DOM, which is why the grouped device list's
  click-through tests didn't need changing.
- **clippy `await_holding_lock`** fires on a `MutexGuard` kept alive to a later `drop()` even with
  no `.await` between — compute what you need inside a `{ }` block instead.

## 10. Conventions that are load-bearing (not style preferences)

- **Never invent Android SDK behaviour.** `sdkmanager`/`avdmanager`/`emulator`/`adb` flag names
  and output formats are load-bearing. Cite the source (official docs, or `--help` captured into
  a fixture under `crates/emu-android/tests/fixtures/`) in a comment, and parse against the
  fixture. When there's no fixture, parse *defensively* (take the first plausible token, return
  `None`/skip on any mismatch) so a weird ROM yields a blank, never a wrong value — see
  `device_facts` and the `sdkmanager` progress path, which deliberately forward raw lines rather
  than guess a percentage format.
- **Every user-facing string is real and specific.** No "An error occurred". Errors say what
  happened and what to do.
- **Scope discipline.** A task lists the files it touches. Touch those. A new cross-cutting
  concern is a new task or an ADR, not scope creep. If a task turns out wrong or too big, edit
  the task file and say so — don't sprawl.
- **The paper trail is the handoff.** Nothing important lives in a tool's private memory. Task
  files, journal entries and `PROGRESS.md` are how the next person (or the next session) picks up
  exactly where this one stopped. `docs/prompts/handoff.md` is the mid-stream handoff procedure.
