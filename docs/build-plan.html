EmuManager Build Plan

A cross-platform desktop app to create, launch, track, and share Android emulators — no Android Studio, no terminal. This is the plan for building it with AI coding agents, in a way that survives switching between them.

Status: pre-M0 · repo scaffolded
Scope
Android only (ADR 0003)
Stack
Tauri v2 · Rust · React/TS
Sharing
Recipe-only .emuprofile
Targets
Windows · Linux · macOS

01

What we’re building

From a fresh machine, EmuManager installs every Android SDK component it needs into its own data directory — command-line tools, platform-tools, the emulator engine, system images — then lets you browse device models, create an emulator, launch it, watch its logs, and track every emulator you’ve made across restarts. Export one as a portable .emuprofile recipe; import it on another machine and it resolves what’s missing, downloads it, and recreates the instance.

Not in v1: iOS simulators (they cannot run off macOS — ADR 0003), physical-device mirroring, cloud/remote emulators, APK building, and cross-machine snapshot bundles (recipes carry no binaries — ADR 0004).

Full detail: docs/spec.md. Design: the four wireframes in docs/design/.

02

Architecture

A Tauri v2 shell over a Rust workspace. The rule that keeps it honest: crates/emu-core holds all domain logic and depends on tauri nowhere — so it stays testable with cargo test alone. src-tauri is glue. Every side effect (spawning a process, downloading, probing the host) is a trait with a real impl and a test fake.

The Rust↔TS boundary is generated by tauri-specta into src/lib/bindings.ts — hand-editing it fails CI. Long operations are jobs that stream job://progress and job://log events; the UI never blocks. The registry stores our metadata but re-reads ground truth from avdmanager list avd / adb devices on every launch, so it never lies about state. Full detail: docs/architecture.md.

03

Developing across AI harnesses

The whole project context lives in plain committed files, so work can move between Claude Code, Cursor, Gemini, Antigravity, or anything else without losing a thing. AGENTS.md is the single operating manual. Each tool’s native config file is a two-line pointer to it with no copied content — only CLAUDE.md and GEMINI.md exist today; adding a tool means adding one more one-line stub, never pasting rules (ADR 0005).

Switching tools is a handoff: finish a coherent slice, run just validate, update the task file + .agent/state.json + PROGRESS.md, and leave a journal entry whose “next action” line can be started cold. Recipe: docs/playbooks/bootstrap-new-harness.md. Handoff prompt: docs/prompts/handoff.md.

07

Progress tracking

The loop

Pick the next todo task for currentMilestone → implement in its file scope → just check-fast → just validate → update the four progress surfaces → commit (Conventional Commits, referencing the task id).

Task lifecycle

todo → doing → review → done  (plus blocked). One task doing at a time. just progress fails the build if a task file and state.json disagree.

Four surfaces move together on every task transition (docs/playbooks/update-progress.md): the task file (tick real criteria, set status), .agent/state.json (machine-readable state + lastValidatedCommit), PROGRESS.md (narrative + milestone checkboxes), and a journal entry (dated handoff note). scripts/progress-check.mjs is the guardrail and already runs today.

Getting started

just setup      # toolchains + dev deps + git hooks (idempotent)
just dev        # run the app
just validate   # the full gate — what CI runs
just progress   # check the tracking files are consistent

New tool? Point it at AGENTS.md, read the newest .agent/journal/ entry, run just progress, and start at the next todo task. That’s the whole onboarding.
